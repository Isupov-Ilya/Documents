# **Техническое задание на разработку программы автоматического формирования биографий по аудиозаписям интервью**

**Версия:** 1.0\
**Статус:** проектное ТЗ для начала разработки\
**Платформа:** Windows\
**Режим:** полностью локальный, без подключения к интернету\
**Способ разработки:** Python с использованием ИИ-агента в редакторе кода

Документ подготовлен на основании шести раундов предпроектного интервью и заключительных уточнений.

## **1. Назначение системы**

Разработать автономную программу, которая преобразует аудиозапись интервью в структурированный биографический документ формата DOCX.

Программа должна самостоятельно распознавать русскую речь, определять участников разговора, извлекать биографические сведения о респонденте и упомянутых третьих лицах, восстанавливать хронологию событий и создавать документ по заранее загруженному образцу.

**Основной сценарий:** пользователь выбирает аудиофайл, выбирает профиль шаблона, нажимает «Начать обработку» и получает готовый DOCX, который подлежит обязательной проверке человеком.

Вмешательство пользователя допускается при низкой уверенности определения говорящего и во время первоначальной настройки шаблона.

## **2. Границы проекта**

**Входит в первую версию**

Поддержка аудио iPhone, распознавание и диаризация, две версии транскрипции, извлечение фактов, создание биографии по DOCX-шаблону, проверка полноты, сохранение этапов, остановка и возобновление, настройки моделей, офлайн-работа.

**Допускается реализовать позднее**

Расширенный поиск по истории, удобный менеджер моделей, дополнительные профили производительности, автоматическое сравнение нескольких версий биографии.

**Не входит в первую версию**

Android-приложение, запись с микрофона, облачная обработка, совместная работа через сервер, встроенный полнофункциональный редактор Word.

## **4. Требования к обработке аудио**

Программа должна принимать записи продолжительностью обычно 30–60 минут, сделанные на iPhone в офисных условиях. Допускаются шумы, паузы, перебивания и непоследовательный разговор.

Обработка выполняется локально.

### **4.1. Диаризация**

Система должна:

1. Выделять речевые фрагменты и определять принадлежность реплик говорящим.
2. Устанавливать роли «интервьюер», «респондент», «третий участник».
3. Использовать контекст разговора для уточнения ролей.
4. При недостаточной уверенности запрашивать подтверждение пользователя.
5. Сохранять подтверждённые роли для дальнейших этапов.

Необязательная стартовая фраза может использоваться как дополнительный сигнал.

Например, интервьюер произносит:

> «Начинаю интервью. Я — интервьюер. Сегодня беседую с респондентом».

Эта фраза не должна быть единственным основанием идентификации. Система должна сопоставлять её с характеристиками голоса и последующими репликами.

### **4.2. Транскрипции**

**Дословная версия** сохраняет содержание реплик, повторы, особенности разговорной речи и обозначения неразборчивых участков. При этом она не может гарантировать буквальное воспроизведение каждого звука.

**Очищенная версия** исправляет пунктуацию и грамматику, устраняет речевой мусор и очевидные повторы, но не должна удалять самостоятельные факты или изменять смысл.

В обеих версиях необходимо сохранять принадлежность реплик говорящим.

## **5. Требования к интеллектуальному анализу**

### **5.1. Извлечение фактов**

Система должна выделять:

- Личные и биографические сведения.
- Образование, трудовую деятельность и иные события.
- Сведения о родственниках, друзьях, коллегах и знакомых.
- Даты, периоды, места, организации и должности.
- Причины событий, если они сообщены.
- Противоречия, приблизительные данные и неопределённости.
- Иные содержательные сведения, не предусмотренные заранее.

Перечень категорий не является закрытым.

### **5.2. Разрешение ссылок на людей**

Каждый упомянутый человек должен иметь внутренний идентификатор.

Система должна понимать, что местоимения и сокращённые упоминания могут относиться к человеку, названному в предыдущих репликах.

Если однозначно установить лицо невозможно, факт не должен автоматически приписываться респонденту.

### **5.3. Контроль достоверности**

Каждому факту присваиваются:

- Источник — реплика или группа реплик.
- Лицо, к которому он относится.
- Статус определённости.
- Признак противоречия.
- Признак логического вывода, если применимо.

Сведения, сообщённые в интервью, следует отличать от независимо проверенных. В первой версии внешняя проверка фактов не предусмотрена.

## **6. Требования к DOCX**

Профиль шаблона должен создаваться на основании одного или нескольких загруженных DOCX с биографиями реальных людей.

Анализатор выделяет структуру, постоянные блоки, переменные сведения, характерные формулировки, таблицы и оформление.

Спорные элементы пользователь подтверждает один раз при настройке профиля.

Система должна поддерживать несколько профилей и версий без удаления предыдущих.

Генерация должна сохранять порядок разделов и хронологию внутри них. Новые разделы допустимы при отсутствии подходящего места для существенных сведений.

Отсутствующие сведения обозначаются фразой «Сведения не представлены» с визуальным выделением. Противоречия и выводы ИИ должны явно маркироваться непосредственно в основном DOCX.

Постоянные текстовые блоки воспроизводятся дословно, но только после подтверждения, что они не содержат персональных данных человека из образца.

# **7. Архитектура программного обеспечения**

# **8. Схемы данных**

Внутренние результаты обработки рекомендуется хранить в JSON с проверкой структуры через Pydantic.

DOCX используется для документов, предназначенных пользователю, а JSON — для передачи данных между этапами.

## **8.1. Схема интервью**

```

{
  "schema_version": "1.0",
  "interview_id": "int_000001",
  "source_audio": {
    "path": "D:/Audio/interview.m4a",
    "sha256": "<контрольная сумма>",
    "duration_seconds": 3540
  },
  "language": "ru",
  "template_profile_id": "bio_main_v1",
  "status": "processing",
  "completed_stages": [
    "audio_preparation",
    "transcription"
  ]
}

```

Система должна сохранять версии схем и предусматривать миграции при обновлении программы.

## **8.2. Схема реплики**

```

{
  "segment_id": "seg_001",
  "speaker_id": "speaker_2",
  "speaker_role": "respondent",
  "start_ms": 12500,
  "end_ms": 18700,
  "text_raw": "Он потом в Самару переехал...",
  "text_clean": "Он впоследствии переехал в Самару.",
  "role_confidence": 0.91,
  "requires_review": false
}

```

Поле `role_confidence` — нормализованная оценка системы, а не автоматически достоверная вероятность. Способ её вычисления и пороги уточнения нужно определить экспериментально.

Временные метки сохраняются внутри проекта, но могут не выводиться в DOCX.

## **8.3. Схема человека**

```

{
  "person_id": "person_002",
  "name": null,
  "relationship_to_respondent": "father",
  "aliases": [
    "отец",
    "папа",
    "он"
  ],
  "source_segment_ids": [
    "seg_001",
    "seg_002"
  ],
  "identity_status": "inferred_from_context"
}

```

В реальной реализации местоимения лучше хранить как контекстные упоминания с привязкой к репликам, а не как постоянные псевдонимы человека. Это позволит избежать ошибочного объединения разных лиц.

## **8.4. Схема биографического факта**

```

{
  "fact_id": "fact_00042",
  "subject_person_id": "person_002",
  "predicate": "place_of_birth",
  "value": "Саратов",
  "date": {
    "value": "1962",
    "precision": "year",
    "approximate": false
  },
  "source_segment_ids": [
    "seg_014",
    "seg_015"
  ],
  "evidence_type": "reported",
  "certainty": "explicit",
  "has_conflict": false,
  "conflict_group_id": null,
  "requires_review": false
}

```

Рекомендуемые значения `evidence_type`:

- `reported` — прямо сообщено в интервью;
- `inferred` — логически выведено программой;
- `unclear` — невозможно однозначно интерпретировать.

Для противоречий необходимо сохранять оба утверждения и связывать их общим идентификатором группы конфликта.

## **8.5. Схема профиля шаблона**

```

{
  "profile_id": "bio_main_v1",
  "name": "Основная биография",
  "version": 1,
  "reference_documents": [
    "sample_01.docx",
    "sample_02.docx"
  ],
  "base_document": "base.docx",
  "sections": [
    {
      "id": "summary",
      "type": "table",
      "required": true
    },
    {
      "id": "biography",
      "type": "narrative",
      "required": true
    }
  ],
  "fixed_blocks": [],
  "formatting_rules": {},
  "missing_data_style": "highlight"
}

```

В окончательной реализации схема должна быть расширена сведениями о стилях, постоянных абзацах, таблицах, правилах размещения фактов и идентификаторах переменных областей.

**Важно:** персональные сведения из эталонных документов нельзя автоматически переносить в `fixed_blocks`.

# **9. Механизм сохранения и повторной обработки**

Каждый этап конвейера должен иметь состояния:

| Состояние     | Значение                                         |
| ------------- | ------------------------------------------------ |
| `pending`     | Ожидает выполнения                               |
| `running`     | Выполняется                                      |
| `completed`   | Успешно завершён                                 |
| `failed`      | Завершён с ошибкой                               |
| `cancelled`   | Остановлен пользователем                         |
| `invalidated` | Результат устарел после изменения входных данных |

После завершения этапа система сохраняет его результат и контрольную информацию.

При повторном запуске программа проверяет:

1. Существуют ли результаты предыдущих этапов.
2. Не изменился ли исходный файл.
3. Не изменились ли модель и настройки, влияющие на результат.
4. Не изменился ли профиль шаблона.
5. Какие зависимые этапы необходимо повторить.

Пример: изменение шаблона требует повторной генерации и проверки DOCX, но не транскрипции. Изменение распознанного текста требует повторного извлечения фактов и всех последующих этапов.

Сохранение должно выполняться через временный файл с последующей атомарной заменой в пределах одного файлового тома, где это поддерживается. При работе с внешними дисками нужно дополнительно обрабатывать отключение накопителя и ошибки записи.

# **10. Конфиденциальность и эксплуатация**

Система должна быть рассчитана на обработку персональных данных респондента и третьих лиц.

Обязательные меры:

- Запрет сетевых запросов во время обработки, включая телеметрию и автоматические обновления.
- Установка моделей и зависимостей из локальных пакетов.
- Хранение исходных материалов только в выбранных пользователем каталогах.
- Отсутствие полных текстов интервью в обычных диагностических журналах.
- Очистка временных файлов с чувствительными сведениями после завершения обработки.
- Использование прав доступа Windows.
- Возможность удаления проекта и его производных данных.
- Проверка наличия исходного аудио перед повторной обработкой.

Отсутствие встроенного шифрования соответствует вашим требованиям, но не заменяет организационные меры защиты, включая BitLocker при необходимости, резервное копирование и ограничение доступа к папкам.

Для реальных интервью следует обеспечить правомерность записи и последующей обработки персональных данных, в том числе сведений о третьих лицах.

## **11.2. Как создавать тестовые данные**

Предлагаю разработать генератор тестовых биографий с вымышленными персонажами.

Для каждого персонажа формируется:

1. Структурированный набор достоверных для сценария фактов.
2. Сценарий интервью, содержащий эти факты в перемешанном порядке.
3. Аудиозапись диалога с двумя или тремя различимыми голосами.
4. Эталонная транскрипция с указанием говорящих.
5. Эталонная структура фактов.
6. Эталонный DOCX.

Аудио можно синтезировать локальными TTS-моделями, лицензии которых разрешают такое использование. При этом синтетическая речь не воспроизводит все сложности реальных интервью, поэтому результаты на таком наборе нельзя считать окончательным доказательством качества в реальной эксплуатации.

# **14. Критерии готовности первой версии**

Программа может считаться готовой к ограниченному использованию, когда:

Окончательные численные пороги качества необходимо утвердить после экспериментального этапа. Целевые 95% полноты и 98% правильной привязки фактов к людям могут использоваться как ориентиры, но пока не подтверждены испытаниями.
